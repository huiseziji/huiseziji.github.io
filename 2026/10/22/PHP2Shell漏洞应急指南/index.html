PHP2Shell 核弹漏洞全记录：CVSS 9.2 的 PHP 内核 RCE，如何发现、如何自查、如何修复

2026 年 10 月 20 日晚上，安全圈的群里开始流传两个还没正式公布的 CVE 编号。到 21 日凌晨，包含「php2shell」攻击链的演示视频已经出现在社交平台上，watchTowr 确认复现了其中一个。PHP 官方原本计划 22 日做的协调披露，被迫提前到了 21 日。

被泄露的两个漏洞是 CVE-2026-109618 和 CVE-2026-109619，官方评级都是 CVSS v4.0 9.2，类型是未认证远程代码执行。PHP 安全团队的原话是「十多年来 PHP 面临的最严重安全事件」。

这篇把三件事讲清楚：这个洞是怎么被找到的、你的服务器到底中不中、以及除升级之外哪些动作纯属自我安慰。

二、为什么它能叫「核弹级」

不是标题党，有三个叠加因素。

第一，漏洞在解释器内核，不在扩展、不在框架。 你用的是 WordPress、Laravel、ThinkPHP 还是自己写的一坨原生代码，没有任何区别——只要底下这个 PHP 运行时没修，风险一样。这也意味着「我们没用那个组件」这类排除法全部失效。

第二，不需要认证。 一个构造好的 HTTP 请求就够了，不需要账号、不需要后台入口、不需要任何前置条件。

第三，PHP 的存量太大了。 PHP 在已知服务端编程语言中的占比长期在七成以上。按「泄露演示涉及的框架」做的资产测绘，量级是这样的：

应用 / 框架 全球可探测资产 国内资产
WordPress 7,226 万 88.7 万
Drupal 169.7 万 6.08 万
Joomla 100.0 万 1.27 万
Laravel 40.6 万 6.57 万
MediaWiki 14.3 万 1,849
ThinkPHP（未在演示中，建议一并排查） 57.3 万 44.4 万

（数据来源为第三方测绘平台，仅作排查范围参考，不代表官方确认。）

更麻烦的是部署形态全覆盖：PHP-FPM、Apache 的 mod_php、php-cgi、FrankenPHP、LiteSpeed 都在影响范围内。官方特别点名 mod_php 风险最高——已有演示表明，一个未认证请求可以在任何应用代码执行之前触发攻击。也就是说你的业务代码、你的框架中间件、你的入口过滤，在这条链路上根本没有出场机会。

三、两个洞到底错在哪

CVE-2026-109618：OOM 处理时的内存损坏

PHP 用 memory_limit 限制单次请求的内存，超限的实现方式是 longjmp()——直接跳走，打断当前执行流程，抛一个内存耗尽的致命错误。

问题在于，这个「跳走」是硬跳。如果它发生在某个内部数据结构只初始化了一半的时刻（比如正在解析表单上传），PHP 就带着一个残缺的状态离开了。等到请求结束做清理，清理代码看到的是「一个合法的结构」，于是去释放那些从来没被初始化过的指针。

而这些内存位置，可能还残留着攻击者在前一次分配里塞进去的数据。清理动作 + 攻击者可控的内存 = 可被引导的内存破坏，进而 RCE。

关键在于：memory_limit 是用户可以间接影响的。你发一个足够大的请求，就能把这个限额打爆，也就等于自己按下了跳转的扳机。

CVE-2026-109619：上一个请求的「残影」

第二个洞的思路完全不同，它利用的是进程复用。

PHP-FPM 的 worker 是常驻的，一个进程要连续处理成千上万个请求。正常情况下，每个请求开始时会重置全局状态。但如果某个请求的内部状态在它背后的内存已经被释放之后仍然存在（例如一次致命错误之后），而这份状态又没被下一次初始化完全覆盖，那么下一个请求就会用到这份「过期数据」。

这是一种典型的状态残留（stale state）问题：单看一个请求它是正常的，问题出在「上一个请求给下一个请求留了什么」。这也是为什么这类漏洞特别难靠常规扫描发现。

所以「我只用 FPM 不用 mod_php」能免责吗

不能。FPM 的暴露路径和 mod_php 不同，但同样在影响范围内，而且 FPM 的 worker 复用模型恰恰是第二个洞成立的前提。官方给的判断是：所有对外提供 Web 请求的 PHP 安装都受影响。

四、这个洞是怎么被发现的

这一节可能比漏洞本身更有意思。

2024 年就有人看见苗头

PHP 核心开发者在 2024 年就注意到相关内存问题的迹象。但他们找不到利用路径，于是修复工作停在那里。

这是内存安全类漏洞的常态：一个「看起来不对」的指针释放，离「能稳定 RCE」之间隔着很远——要能控制内存布局、要能绕过分配器的随机性、要能在真实 SAPI 里复现而不是在单元测试里。找得到 bug 和打得通利用，是两个难度级别。

2026 年 8 月，AI 把这段距离抹平了

公开报道的说法是：安全公司 Calif 的研究员 Ryan Austin 在对 PHP 源码做审计时，借助 OpenAI 的模型，把这一潜伏多年的内存缺陷变成了可工作的 RCE 链。同期，Wiz 用 AI 代理独立发现了第一个漏洞，次日就实现了针对 Drupal 的未认证代码执行。

我不打算在这里讨论「AI 是不是真的挖到了洞」这种口水问题，只说我看到的、对防守方真正有影响的部分：读代码找内存问题的成本，被显著打下来了。

以前这类工作依赖少数懂 Zend 引擎内部结构的人，靠年为单位的时间积累直觉。现在一个有源码审计经验、但不懂 PHP 内核的人，可以借助模型做跨函数的追踪和假设生成，把「可疑的 longjmp 路径」一条条筛出来。搜索空间没变，但搜索速度变了。

披露被打乱，防守窗口直接归零

原计划的协调披露是 10 月 22 日。10 月 20 日匿名帖出现，附带了两个 CVE 编号；随后攻击链演示视频流出，watchTowr 复现成功。

于是官方在 21 日提前发版。TechWeb 的报道里提到，有安全公司判断补丁发布后约 15 分钟就可能开始大规模攻击；watchTowr 在补丁落地前后已观察到利用尝试，Cloudflare 也报告了攻击流量。

研究者视角：这类漏洞该怎么找

如果你也想做这种工作，路径其实是可以复述的，不是玄学：

  1. 盯住「中断路径」。longjmp、异常、超时、致命错误——所有「执行流被强行打断」的地方，都是「只初始化了一半」的高发区。重点看这些路径触发后，request shutdown 阶段会怎么处理这些半成品。
  2. 用 ASAN 构建 PHP。内存问题在普通构建下往往只是「偶发崩溃」，在 AddressSanitizer 下会变成明确的「读/写已释放内存 + 调用栈」。这一步能把 90% 的噪音过滤掉。
  3. 把阈值调到极限。既然 618 的入口是 OOM，就把 memory_limit 压到很低，构造刚好越过边界的请求，看清理阶段的行为。漏洞往往藏在「刚好失败」的临界点上。
  4. 做双请求差分。619 这种状态残留，单请求测试永远发现不了。要写「请求 A 制造异常 → 请求 B 观察状态」的测试，而且必须在同一个 worker 进程里连续发。
  5. Fuzz SAPI 入口，而不是 fuzz 单个函数。真实攻击面在请求解析层，不在业务函数里。

这套方法的每一条，恰好都是 AI 模型擅长的事：跨函数追踪数据流、根据调用栈反推前置条件、批量生成边界用例。这大概就是「一年没打通，一夜之间打通」的原因。

五、自查：你的 PHP 到底跑的是哪个版本

这是全文最该动手的一节。判定的核心不是「装了什么」，而是「正在跑的是什么」。

第 1 步：把资产清全

别只数网站。真实环境里最容易漏的是这些：

位置 典型情况
Web 站点 FPM pool、Apache mod_php、IIS + php-cgi
CLI 脚本 定时任务、数据导出、运维脚本
常驻进程 队列 worker、Swoole / RoadRunner 常驻应用
面板自带 宝塔、Plesk 的 PHP 与系统 PHP 是两套独立安装
容器 每个镜像都自带一份，宿主升级与它无关
被遗忘的机器 测试机、旧虚拟机、外包交付后没人管的服务器

面板环境要特别提醒一句：系统级 PHP 和面板托管的 PHP 是两套。只升级其中一个，站点绑定的 handler 可能还在旧版本上，页面看起来一切正常。

第 2 步：查版本号

判定标准很直接：

分支 受影响 修复版本
8.5 < 8.5.12 8.5.12
8.4 < 8.4.27 8.4.27
8.3 < 8.3.36 8.3.36
8.2 < 8.2.35 8.2.35（该分支 2026-12-31 停止支持）
8.1 及更早 受影响 无官方修复

第 3 步：查「正在跑的」进程

这一步比第 2 步重要，而且最容易被跳过。

php -v 输出的是命令行二进制的版本。真正对外服务的是 FPM master、Apache 子进程、常驻 worker——它们加载的是启动那一刻内存里的代码。你上午 9 点启动的服务，晚上 10 点升级了包，php -v 会告诉你新版本，但正在跑的进程仍然是旧的。

判断方法只有一个：比时间。

如果进程启动时间早于二进制修改时间，那这个进程加载的仍然是旧代码，等于没修。

容器环境还有一个额外的坑：docker restart 不会让镜像里的 PHP 变新。镜像里的二进制是构建时打进去的，必须重新构建镜像并滚动更新，确认所有副本都换到新镜像。

第 5 步：翻日志，看有没有已经被打过

这个洞有个特点：它在应用代码之前触发。 所以业务日志很可能干干净净，什么异常都没有。要看的反而是底层的日志：

值得关注的现象：

  • worker 反复因 SIGSEGV 退出、被 master 重启，表现为间歇性 502
  • Allowed memory size ... exhausted 异常增多，且集中在几个来源 IP
  • 访问日志里出现「字段极多 / multipart 段极多 / 没有 Content-Length 的超大请求」——这正是打 618 的典型特征
  • 同一 IP 在短时间内触发大量 4xx/5xx，紧接着服务短暂不可用

关于「直接拿 PoC 打一下验证」

别在线上做。

三个理由：第一，这个漏洞的利用效果本身包含进程崩溃（618 的路径就是内存损坏），拿生产流量去打，轻则 worker 崩一片，重则真的把自己打进去；第二，PoC 已广泛流传，攻击者也在扫描，你手动打的流量会混进真实攻击里，事后取证根本分不清；第三，这个漏洞的判定根本不需要 PoC——它是「版本号即判定」的类型，8.3.35 < 8.3.36，结论就定了。

真要验证，就在隔离环境里做：打快照、断外网、用公开的复现脚本跑一遍，观察是否出现 worker 崩溃或异常子进程，验完直接销毁快照。目的不是「证明能打穿」，而是「确认我的检测规则能看见它」。

六、修复：升级之外都是减速带

1. 唯一正确的解药

升级到 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 之一。官方说得很直白：没有任何完整的缓解措施，升级是唯一安全的选择。

2. 按来源选路径

安装来源 做法
发行版包 apt upgrade / dnf update，发行版和 LTS 厂商提前拿到了补丁
官方源码 / Windows 二进制 php.net 下载页
容器镜像 重新构建镜像，滚动更新，不能只 restart
自编译 拉官方 tag 重新编译
rpms.remirepo.net 官方明确说当天不会有更新，建议换发行版源或源码编译
PHP 8.1 及更早 无官方修复。官方为 7.4 / 8.0 / 8.1 提供了最小化源码 backport 分支，供自行编译；否则升级到受支持分支

7.4 / 8.0 / 8.1 的 backport 分支在 php-src 仓库里，名字是 PHP-7.4-CVE-2026-109618-109619 这种格式，适合「必须留在老版本、但有能力自己编译」的场景。没这个能力的话，唯一的出路是升级。

3. 升级之后必须重启（最常被跳过的一步）

  • mod_php：重启 Apache
  • PHP-FPM：重启对应的 FPM 进程池
  • 常驻 CLI（队列 worker、守护脚本）：逐个重启
  • 容器：重建镜像 + 滚动更新

再强调一次：不能靠 php -v 判断修复完成。 它反映的是磁盘上的二进制，与正在提供服务的进程无关。用第五节的「比时间」方法确认。

4. 怎么确认真的修好了

三条，缺一不可：

  1. 进程实际加载的版本——用「进程启动时间晚于二进制更新时间」确认，而不是 php -v。
  2. 业务回归——升级 PHP 小版本通常安全，但生产环境该做的回归还是要做。
  3. 资产清单全覆盖——对照第一步的清点表逐项销账。遗漏的实例必须单独登记为遗留风险，不能算「已修复」。

5. 实在升不了：官方给的缓解清单

必须先说清楚：这些措施只降低特定攻击路径的暴露面，不能让安装变安全。

针对 CVE-2026-109618（OOM 路径）：

设成 -1 的目的是取消用户可控的内存限额失败，从根上拆掉扳机。但要检查：没有别的 pool、目录级配置或应用里的 ini_set 又把它设回来。另外，底层分配失败仍然可能走到那条路径，所以这不是安全保证。

同时压低请求体：

更稳的做法是在 Nginx / 网关层限制解码后的请求大小、字段数量、multipart 段数、header 数量和嵌套深度，而且要覆盖没有 Content-Length 的 chunked 请求——只靠 PHP 层的大小限制会被分块绕开。

针对 CVE-2026-109619（状态残留路径）：

关键是必须重启所有 worker，而且必须写在 php.ini、FPM pool 配置或服务器配置里——ini_set() 和 .user.ini 在请求解析前不生效，写了等于没写。

另外两条：清掉那些「每次请求都会产生诊断输出」的废弃配置项（把 error_reporting 调低或加 @ 压制是没用的，诊断本身已经发生了）；修掉攻击者可触达的致命错误和执行超时。

6. 明确无效的动作

这几条别浪费时间：

  • **disable_functions、open_basedir**：它们工作在脚本层。这个漏洞在原生代码层就劫持了执行流，压根到不了函数调用。
  • 封 SSH 端口：入口是 80/443，跟 22 没关系。
  • 只靠 WAF：新漏洞没有现成规则，虚拟补丁只能当辅助。而且已经有报告说攻击者在调整载荷绕过规则。
  • 把 display_errors 关掉：这不叫修复，叫「看不见」。

七、如果怀疑已经被打了

顺序别乱，先控损再取证：

  1. 隔离：把实例从负载均衡摘掉，或直接断外网。别急着重启——内存里的残留状态可能是唯一的证据。
  2. 留证：内存镜像、进程列表、网络连接、/tmp 和 web 目录的近期变更、cron 和 systemd 单元。
  3. 查落地：Web 目录里新出现的 .php 文件（尤其是文件名随机、内容混淆的）、.htaccess 改动、上传目录里的可执行文件。
  4. 查持久化：crontab -l、/etc/cron.*、systemd 单元、~/.ssh/authorized_keys、.bashrc。
  5. 改密：数据库账号、API Key、云厂商凭据、.env 里的所有东西——这些是最常见的窃取目标。改完再去查有没有被用来横向移动。
  6. 复盘：这次是「应用日志干净但 worker 崩过」还是「什么都没发现」？后者更危险，说明检测根本没覆盖到。

八、三条该记住的教训

第一，「这是个组件漏洞，不影响我们」的思路要改。 这次在解释器内核，下次可能是运行时、是 libc、是内核本身。判断影响面要看依赖层级，不是看有没有装某个插件。

第二，补丁窗口正在消失，甚至变成负数。 这次细节在补丁前泄露，攻击者可以和防守方同时起跑，甚至更早。这意味着「等公告、走流程、排期升级」的节奏已经不成立，资产台账 + 自动化升级通道才是真正的护城河。你不知道自己有哪些 PHP，就没法在 15 分钟内做出反应。

第三，遗留系统是长期出血点。 PHP 7.4 至今仍是可识别版本中占比最高的单一分支。这些机器嵌在遗留应用、共享主机、被遗忘的虚拟机里，很多永远不会被打补丁。它们不构成「某一晚的危机」，而是构成一个以年为单位的风险面。

至于 AI 在这件事里的角色——它既让漏洞被发现得更快，也让补丁被逆向成利用代码的速度更快。攻防两侧都在加速，唯一没加速的是很多组织的响应流程。
